# 이슈·PR 컨벤션

작성자 이름(`[이름]` 자리)은 `~/.claude/CLAUDE.md` 의 "작성자" 항목을 쓴다.

## 제목
| 대상 | 형식 | 예 |
|---|---|---|
| 이슈 | `타입: [이름] 내용` | `feat: [강철웅] 로그인 API 구현` |
| PR | `타입: [이름] 내용 (closes #이슈번호)` | `feat: [강철웅] 로그인 API 구현 (closes #12)` |
| 커밋 | `타입: 요약` | `feat: 로그인 API 추가` |

타입은 `feat`, `fix`, `chore`, `refactor`, `docs`, `test` 등 커밋 타입과 같다.

## 이슈
- 레포에 `.github/ISSUE_TEMPLATE/` 가 있으면 그 템플릿 형식을 그대로 채운다.
- 없으면 `Description / To-do / 기타` 로 쓴다. To-do 는 체크박스로 적는다.
- 이슈 하나에 PR 하나가 기본이다.

## PR
- 레포에 `.github/PULL_REQUEST_TEMPLATE.md` 가 있으면 그 섹션을 따른다. 없으면 아래를 쓴다.
- **본문은 자세히 쓴다.** 리뷰하는 사람이 코드를 열기 전에 흐름을 알 수 있어야 한다.

| 섹션 | 내용 |
|---|---|
| 개요 | 무엇을 왜 하는 PR 인지 2~3문장 |
| 작업 내용 | 클래스·파일 단위로 무엇을 어떻게 바꿨는지, 고려한 대안과 선택 이유 |
| API 변경 | 추가·변경된 API (메서드, URL, 요청·응답, 에러 케이스) |
| 테스트 | 실행한 명령과 결과 숫자 (예: `./gradlew test` → 24 passed), 수동 검증 내용 |
| 스크린샷·영상 | 화면 변경이 있을 때 |
| 관련 이슈 | `closes #번호` |
| 리뷰 포인트 | 특히 봐주었으면 하는 부분, 알려진 한계, 추후 계획 |

- base 브랜치는 프로젝트의 기본 브랜치다. (보통 `develop`) 올리기 전에 base 가 맞는지 확인한다.
- 리뷰어는 프로젝트 컨벤션에 따라 지정한다. 모르면 사용자에게 묻는다.
- PR 은 사용자가 요청할 때만 만든다. 먼저 나서서 만들지 않는다.
