# 설계 · 기능 문서

규칙은 `~/.claude/rules/docs-management.md` 를 따른다.

## 절차
1. **범위 확인**: 이슈 번호와 문서로 남길 작업 범위를 확인한다. 위치는 프로젝트 `CLAUDE.md` 가 정한 곳, 없으면 `docs/design/{이슈번호}-{설명}.md`
   - 같은 이슈의 문서가 이미 있으면 **갱신 모드**로 진행한다.
2. **근거 수집**: 이슈 본문(`gh issue view`), 커밋, `git diff <base>...HEAD`, 컨트롤러·DTO·ErrorCode 를 실제로 읽는다. 읽지 않은 것은 쓰지 않는다.
3. **새 문서 섹션**
   - 배경 (왜 필요했는지)
   - 구현 내용 (주요 클래스와 흐름)
   - API 명세 (메서드, URL, 요청, 응답, 에러 케이스를 표로)
   - 설계 결정 (왜 이렇게 했는지, 고민한 다른 선택지)
   - 검증 (어떻게 확인했는지)
   - 남은 이슈
   - `closes #이슈번호`
4. **갱신 모드**
   - 문서의 코드 조각, 경로, 시그니처를 실제 코드와 하나씩 대조해 달라진 곳만 고친다. (Edit 으로 최소 diff)
   - 해결된 TODO 는 지우지 않고 ~~취소선~~ 처리 뒤 "해결됨(어떻게)"을 덧붙인다.
   - 건드리지 않는 것: 제목, `closes #…`, 배경의 원래 취지, 과거 검증 기록
5. 코드에서 확인되지 않는 내용은 단정하지 않고 사용자에게 묻는다.
6. 끝나면 어떤 섹션을 왜 고쳤는지 3~5줄로 요약한다. 문서 파일만 쓰고 **커밋하지 않는다.** (커밋은 `commit-plan`)
