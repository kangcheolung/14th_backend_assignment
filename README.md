# 주제

과제전형 대비 코테이토 14기 백엔드 학기 중 과제 (1~6주차)

---

# 1. 목표

이 문서는 1주차부터 6주차까지 다룰 **과제의 전체 흐름**을 먼저 이해할 수 있게 정리한 문서이다.

프로젝트를 처음 접하는 사람도 기본기부터 쌓고, AI를 활용하는 방법을 익히고, 마지막에는 요구사항만 보고 백엔드와 프론트까지 직접 만들어 보는 것이 목표다.

이 문서에서는 다음 내용을 먼저 정리한다.

- 이 과제를 왜 만들었는지
- 전체 구성을 어떻게 잡았는지
- 각 단계에서 어떤 문제를 다루는지
- 각 문제가 몇 주차 과제와 연결되는지
- 1주차부터 6주차까지 어떤 순서로 진행되는지
- 프로젝트를 어떻게 실행하는지

각 주차의 자세한 내용은 노션 링크에서 확인한다.

---

# 2. 문제 정의

백엔드 지원자에게 과제전형은 자주 만나게 되는 평가 방식이다.

과제전형에서는 요구사항을 읽고, 스스로 설계하고, 실제로 동작하는 결과물로 제출해야 한다. 코테이토 14기 백엔드 파트장으로서, 이 경험을 학기 중에 미리 해 볼 수 있도록 이 과제를 만들었다.

그런데 참가자 중에는 프로젝트를 처음 접하는 사람도 있다.

처음부터 요구사항을 주고 알아서 만들게 하면 어디서부터 시작해야 할지 막막할 수 있다.

그래서 과제를 아래처럼 나누었다.

```
1~3주차: 프로젝트 초기 설정
4주차:   AI 활용 (하네스 엔지니어링)
5~6주차: 요구사항을 보고 백엔드 + 프론트 개발
```

이번 과제에서 사용할 기본 가정은 다음과 같다.

```
대상: 코테이토 14기 백엔드 파트 참가자
수준: 프로젝트를 처음 접하는 사람도 포함
기간: 1주차부터 6주차까지
최종 결과물: 요구사항을 보고 직접 만든, 동작하는 백엔드 + 프론트 프로젝트
```

즉, 앞 주차는 뒤 주차를 위한 준비 단계이고, 마지막 5,6주차에서 과제전형과 같은 형태의 결과물을 직접 만들어 본다.

---

# 3. 기본 설계 방향

이번 과제는 아래 구조를 기본 방향으로 잡는다.

1. 1~3주차에서 프로젝트의 뼈대를 만든다. (Git, Swagger, 환경 설정, 공통 응답, 예외 처리, CORS, Security, BaseEntity)
2. 4주차에서 AI가 우리 프로젝트의 규칙대로 일하게 하는 환경(하네스)을 만든다.
3. 5~6주차에서 이 뼈대와 하네스를 그대로 가지고 요구사항을 보고 백엔드와 프론트를 함께 개발한다.
4. 백엔드와 프론트는 한 레포(모노레포)에서 관리한다.
5. 마지막에는 Playwright E2E로 프론트와 백엔드가 같이 동작하는지 검증한다.

전체 흐름을 간단히 보면 다음과 같다.

```
Git / GitHub
→ Swagger, .env 설정
→ 공통 응답, 예외 처리, CORS, Security, BaseEntity
→ 하네스 (CLAUDE.md, rules, skills, hooks)
→ 요구사항을 보고 백엔드 + 프론트 개발 (모노레포, JWT)
→ Playwright E2E로 연동 검증
```

# 5. 단계별로 다루는 문제와 해결 방향

## 문제 1. 프로젝트를 처음 접해서 어디서부터 시작할지 모르는 문제

프로젝트를 처음 해 보는 사람은 Git, 문서화, 환경 설정부터 막힐 수 있다.

처음부터 큰 요구사항을 주면 시작하기 어렵다.

### 해결 방향

처음 3주 동안은 기능을 만드는 것보다 프로젝트의 기본 환경을 갖추는 데 집중한다.

Git과 GitHub 사용법, Swagger와 `.env` 설정을 먼저 익히고, 같은 프로젝트 위에 다음 주차를 쌓는다.

### 관련 주차

```
1주차: Git & GitHub
2주차: Swagger, .env 파일 설정
```

---

## 문제 2. API 응답과 에러 형식이 제각각이면 프론트가 불편한 문제

API마다 응답 구조가 다르면 프론트엔드는 매번 다르게 파싱해야 한다.

에러가 났을 때도 무슨 문제인지 알기 어렵다.

### 해결 방향

성공 응답(`ApiResponse`)과 실패 응답(`ErrorResponse`)을 하나의 형식으로 통일하고, `ErrorCode` enum 하나에 에러 정보를 모아서 관리한다.

프론트와 통신하기 위한 CORS, Spring Security 최소 설정, `createdAt`/`updatedAt`을 자동으로 채우는 `BaseEntity`도 이 단계에서 만든다.

### 관련 주차

```
3주차: 공통 응답, CORS, Security, BaseEntity 설정
```

---

## 문제 3. AI를 쓰기는 하는데, 프로젝트 규칙대로 일하게 만들 줄 모르는 문제

AI는 요청한 대로 코드를 짜 주지만, 우리 프로젝트의 규칙과 구조를 모르면 매번 같은 실수를 반복한다.

### 해결 방향

AI가 프로젝트를 이해하고 규칙을 지키도록 하네스를 직접 만든다.

- `CLAUDE.md`: 프로젝트 개요와 규칙을 AI에게 알려 주는 파일
- rules: 상황별로 따르는 규칙
- skills: 반복되는 작업의 절차
- hooks: 위험한 행동을 실행 직전에 막는 장치

이렇게 만든 하네스는 5,6주차에서 그대로 이어서 사용한다.

### 관련 주차

```
4주차: 하네스 엔지니어링
```

---

## 문제 4. 요구사항만 보고 프론트까지 연결해서 완성해야 하는 문제

과제전형에서는 요구사항 문서를 보고 백엔드와 프론트를 직접 연결해서 동작하는 결과물을 만들어야 한다.

### 해결 방향

스터디 매칭 플랫폼을 요구사항에 맞게 만든다.

백엔드와 프론트를 한 레포(모노레포)에서 관리하고, 인증(JWT), 스터디 모집글, 댓글(스터디 신청)을 구현한다.

4주차에 만든 하네스를 그대로 가지고 개발하고, 필요하면 규칙을 더한다.

### 관련 주차

```
5,6주차: 요구사항에 맞게 백엔드, 프론트 개발
```

---

## 문제 5. 프론트와 백엔드가 같이 동작하는지 어떻게 확인할지 모르는 문제

화면을 직접 눌러 보며 확인하면 시간이 오래 걸리고, 수정할 때마다 다시 확인하기도 어렵다.

### 해결 방향

Playwright로 E2E 테스트를 작성해서 화면부터 API, DB까지 이어지는 흐름을 명령어 한 줄로 확인한다.

정상 흐름과 에러 흐름을 모두 포함하고, 전부 통과한 결과를 PR에 첨부한다.

### 관련 주차

```
5,6주차: Playwright E2E로 프론트와 백엔드 연동 검증
```

# 6. 과제 진행 시 반드시 지켜야 할 규칙

이번 과제를 진행할 때 아래 조건은 반드시 지켜야 한다.

1. 작업은 이슈 → 브랜치 → PR 순서로 진행한다.
2. PR 제목은 `타입: [이름] 내용 (closes #이슈번호)` 형식으로 쓴다.
3. 커밋은 논리 단위로 나누고, 프로덕션 코드와 테스트 코드는 커밋을 분리한다.
4. `.env`, 비밀번호, JWT 시크릿은 Git에 올리지 않는다.
5. 4주차에 만든 하네스는 이후 주차에서도 계속 이어서 사용한다.
6. 하네스를 새로 추가하거나 고쳤다면 무엇을, 왜 바꿨는지 PR에 기록한다.
7. 5,6주차에서는 E2E를 포함한 테스트가 모두 통과해야 한다.

이 규칙들은 1주차부터 6주차까지 모든 과제에서 계속 기준이 된다.

# 7. 공통 용어 정리

이번 과제에서 자주 나오는 용어는 다음과 같다.

| 용어 | 의미 |
| --- | --- |
| Swagger | API 문서를 자동으로 만들고, 브라우저에서 바로 호출해 볼 수 있게 해 주는 도구 |
| `.env` | DB 접속 정보처럼 코드에 쓰면 안 되는 값을 따로 두는 환경 변수 파일. Git에 올리지 않는다 |
| ApiResponse | 성공 응답을 `success`, `status`, `data`, `timestamp` 구조로 감싸는 공통 클래스 |
| ErrorResponse | 실패 응답을 `code`, `message`, `method`, `path` 등과 함께 감싸는 공통 클래스 |
| ErrorCode | HTTP 상태, 에러 코드(`BOOK-001`처럼 `도메인-일련번호`), 메시지를 한곳에 모은 enum |
| CORS | 다른 출처(프론트엔드 주소)에서 오는 요청을 서버가 허용하는 설정 |
| BaseEntity | `createdAt`, `updatedAt`을 자동으로 관리해 주는 엔티티 상위 클래스 |
| JWT | 로그인 후 발급받아 이후 요청의 `Authorization` 헤더에 붙여 보내는 인증 토큰 |
| 하네스 | AI가 프로젝트 규칙대로 일하도록 만든 작업 환경 (`CLAUDE.md`, rules, skills, hooks) |
| 모노레포 | 백엔드와 프론트엔드를 한 레포에서 관리하는 구조 |
| E2E | 화면 → 프론트 → API → DB 전체 흐름을 사용자처럼 확인하는 테스트 |
| Playwright | 브라우저를 코드로 조종해 E2E 테스트를 만드는 도구 |

# 8. 진행 방식

1주차부터는 아래 순서대로 각 영역을 진행한다.

```
1주차:   Git & GitHub

2주차:   Swagger, .env 파일 설정

3주차:   공통 응답, CORS, Security, BaseEntity 설정

4주차:   하네스 엔지니어링

5,6주차: 요구사항에 맞게 백엔드, 프론트 개발
```

각 주차에서는 이전 주차에서 만든 프로젝트와 하네스를 바탕으로 다음 영역을 더 구체화한다.

따라서 매주 과제는 독립적인 과제이면서도, 마지막에는 하나의 동작하는 스터디 매칭 플랫폼으로 연결된다.

# 9. 실행 방법

`backend/`에 환경 파일(`DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `JWT_SECRET`)이 필요하다. 이름은 `backend/.env.example`에 있다.

```bash
# 백엔드 (8080)
cd backend && ./gradlew bootRun

# 프론트엔드 (3000)
cd frontend && npm install && npm run dev

# E2E (백엔드를 먼저 켜 두기)
cd frontend && npx playwright install chromium   # 처음 한 번
npx playwright test
```

Swagger UI: `http://localhost:8080/swagger-ui/index.html`
